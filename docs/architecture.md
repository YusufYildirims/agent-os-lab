# v0.1 Architecture

v0.1 is an educational userspace coordination layer above Linux. Its only
milestone is collecting system information through a delegated operation.

```text
User -> Orchestrator -> System Agent -> Linux
User <- Orchestrator <- System Agent <- Linux
```

## Component responsibilities

- **User:** requests the supported system-information operation and receives its result.
- **Orchestrator:** validates the request, dispatches it to the System Agent,
  tracks its outcome and timeout, and presents the result. It does not collect
  Linux information directly.
- **System Agent:** implements `get_system_info`, reads a predefined set of
  system observations through known interfaces, and returns structured data or
  an explicit error. It accepts no arbitrary shell commands.
- **Linux:** supplies system information and enforces the application's existing
  process permissions.

The orchestrator and System Agent initially run as separate modules in one
Node.js process. An agent can be a deterministic worker; no LLM is required.

## Request/response contract

Communication uses an asynchronous function call with one request and one
response. No message broker or direct agent-to-agent communication is needed.

Request:

```json
{
  "requestId": "req-1",
  "operation": "get_system_info"
}
```

Success response (illustrative values):

```json
{
  "requestId": "req-1",
  "status": "success",
  "data": {
    "hostname": "linux-host",
    "kernelRelease": "6.8.0",
    "cpuCount": 4,
    "totalMemoryBytes": 8589934592,
    "uptimeSeconds": 1200
  }
}
```

Error response:

```json
{
  "requestId": "req-1",
  "status": "error",
  "error": {
    "code": "COLLECTION_FAILED",
    "message": "Unable to read system information"
  }
}
```

- `requestId` is a nonempty string generated by the orchestrator and echoed in
  the response.
- `operation` must be `get_system_info`; the operation takes no parameters.
- Success includes all five fields: strings for hostname and kernel release,
  a positive integer CPU count, a nonnegative integer memory size in bytes,
  and nonnegative numeric uptime in seconds.
- Responses contain either `data` or `error`, never both. No partial success is
  returned. Error codes are `INVALID_REQUEST`, `COLLECTION_FAILED`, or `TIMEOUT`.
- The orchestrator rejects invalid requests and reports a timeout if collection
  exceeds its configured deadline. A timeout ends waiting; it does not guarantee
  cancellation of the underlying work.

## Boundaries and non-goals

Module separation is an **organizational boundary**, not a **security boundary**.
Both modules share process privileges and memory. A restricted operation
interface expresses intended access but cannot contain a compromised module.
v0.1 does not claim capability enforcement or zero-trust isolation.

Explicit non-goals:

- Developer Agent, autonomous planning, delegation loops, and LLM integration.
- Arbitrary command execution, filesystem modification, and persistent agent memory.
- Distributed services, message brokers, and generic agent frameworks.
- Process isolation, capability enforcement, cgroups, namespaces, and containers.
- AI-aware scheduling, CPU/RAM/GPU allocation, Rust/C components, and kernel changes.

## Evolution toward OS mechanisms

Keep the operation contract independent of its transport so later milestones can
introduce enforceable boundaries incrementally:

1. **Process isolation:** move the System Agent into a separate process with
   reduced privileges; let the orchestrator supervise startup, exit, and termination.
2. **IPC:** carry the same request/response contract over process pipes or Unix
   sockets, adding framing, peer authentication, and message validation as needed.
3. **Capabilities:** grant explicit authority for particular operations and
   resources, backed by OS restrictions rather than module conventions alone.
4. **cgroups:** account for and constrain agent CPU and memory use; use those
   measurements as a basis for later scheduling experiments.
5. **Namespaces:** restrict each agent's view of resources such as processes,
   mounts, and networking. Define whether system information describes the host
   or the agent's isolated environment.

Separate processes alone do not establish least privilege, and namespaces alone
do not provide complete security isolation. Transport, capability representation,
isolation policy, scheduling, and implementation languages remain deferred decisions.
